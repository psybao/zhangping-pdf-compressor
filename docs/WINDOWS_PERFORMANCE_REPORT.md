# Windows 压缩速度核查与优化

张平PDF压缩器 · 开发者：可达包 · 2026-11-18

主要瓶颈是原体积模式固定执行12轮完整压缩，每轮都进行 JPEG/JPEG2000 编码、解码和质量搜索。图片处理比文件哈希和结构验证耗时高得多。原来单图片进程也限制了多图片 PDF 的吞吐。

|测试场景|优化前|优化后|尝试次数|输出字节数|
|---|---:|---:|---|---:|
|scan / 中品质|3.36秒|3.41秒|1 → 1|1,658,118|
|scan / 2097152字节上限|47.82秒|11.65秒|12 → 3|1,658,118|
|mixed / 512000字节上限|47.65秒|9.43秒|12 → 4|414,396|
|多图片PDF / 中品质|6.17秒|3.93秒|图片进程1 → 2|3,288,677|

已实施：中品质起步、相邻参数探测和区间搜索，避免无效的高DPI尝试；满足资源条件时最多2个图片工作进程。实际EXE已启用双图片进程并成功处理4页PDF。Android同步了区间搜索。

仍使用原DPI、质量阈值和编码器，保留文字/矢量/透明度；仍执行原件变化、PDF完整性和实际体积上限检查。以上三组单图测试及多图测试的输出字节数与旧版相同，文字提取验证通过。

这是本机确定性测试样本的冷候选缓存结果。单图三组两版都启用相同Python性能剖析；多图两版都未启用剖析。未使用用户真实PDF，不代表所有文件都能快相同倍数。单图片品质模式本次没有明显变快；JPEG2000质量搜索仍有实际成本。

当前内存策略保守：少图、超大图片、文档总像素过高或可用内存不足时不启用双进程。复杂字体、超多页PDF仍可能耗时。区间搜索选择已验证候选中最接近目标者，并非遍历所有组合；若大小不单调，可能与全遍历结果不同，但绝不发布超过目标的文件。

打开按钮修订：Windows/Android“打开”始终指向源文件，成功后新增“压缩后文件”专门打开结果。帮助按钮改为小圆形半角?。Android实际点击并截获打开Intent，Windows截获打开路径，均验证源/结果分离。
